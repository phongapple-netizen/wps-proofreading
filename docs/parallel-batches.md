# 首轮批次并发与耗时记录

基于 main `e3c7640`。本次只增加首轮有限并发和内存计时；一致性复核仍串行。批大小、提示词、规则语义、文档快照校验和 OpenCode 的 build 代理、所有工具 ask、客户端不批准的限制保持现状。

## 设置与默认行为

- 设置中的“校对并发数”支持 1、2，默认 **2**，包括旧设置缺少该字段时；这会改变原来的串行行为。选择 1 恢复串行调度。并发设置在一次运行开始时固定，编辑只影响下次运行。
- 普通失败或取消停止新批次并取消同一运行的在途请求，保留已完成且快照仍有效的结果。快照失效则丢弃全部结果。没有 AbortController 的旧内核沿用现有取消保护：无法终止传输，但晚响应不能恢复结果或启动新批次。
- 首轮 MODEL_RATE_LIMITED / HTTP 429 暂停新批次，等待在途请求结束后将本次运行并发降为 1，重试受限批次一次。每批最多重试一次；再次失败按原来的部分结果处理。该降级不修改保存的设置，也不自动重试一致性复核。

## 查看日志

设置 → “高级 / 故障排查 · 校对性能” → “记录校对耗时”。默认关闭，各模型通道均可使用。面板打开时自动更新，也可刷新、复制、清空；不支持剪贴板 API 的内核尝试旧式复制，失败时可以手动选中复制。

日志只在当前面板内存保留最近 500 条。重载面板后记录消失，设置开关仍可保存。关闭开关或清空时，已在途的旧计时记录不会重新写入。记录仅包含固定字段和非负数值，不保留正文、提示词、模型回复、错误文本、文档身份、会话 ID、URL 或凭据。

|字段|含义|
|---|---|
|kind|1 模型请求、2 逻辑批次、3 一次运行|
|run / stage / batch / attempt|运行序号；阶段 1 首轮、2 一致性；批次序号；请求尝试次数|
|characters / concurrency|首轮正文字符数；复核请求字符数（含固定指令）；该次请求的并发上限|
|outcome|0 成功、1 失败、2 取消、3 请求受限。运行成功仍可能包含复核警告，具体错误可看复核记录|
|createSessionMs / messageMs / cleanupMs|OpenCode 建立受限会话、发消息到解析返回、清理会话的耗时|
|connectionMs / requestMs|OpenCode 本机服务准备耗时；完整模型请求耗时（含会话清理）|
|pollCount / pollMs|本次请求的审批轮询次数和累计耗时；轮询与模型等待重叠，不能相加解释为总耗时|
|batchMs|包含请求、快照校验、解析、合并及发布的批次耗时；429 的等待与重试计入同一个逻辑批次|
|totalMs|确认选区/全文后，规则扫描、首轮校对及一致性复核的运行耗时；不含用户确认等待|

直连 Ollama / OpenAI 兼容接口没有临时会话，其 requestMs / messageMs 记录完整请求等待。取消或失败时，运行可先结束，后台请求的清理计时可稍后追加。

## 验证与实际对比

main 基线 `npm test` 为 322 项全部通过。新增测试覆盖并发上限、返回顺序、取消/失败、429 串行降级与一次重试、快照失效、迟到响应、重启、设置冻结、内存隐私与容量、OpenCode 三段计时和审批轮询，以及多通道界面的查看/复制/清空。

最终 `npm test`：344 项全部通过，0 失败、0 跳过；`git diff --check` 通过。最后一次模拟测量为串行 309.9ms、并发 2 为 158.3ms，此数值仅用于证明模拟夹具中的调度收益。

自动化模型以四批各延迟 70ms 的模拟响应验证并发 2 比串行更快，问题列表及 ID 相同。**这些是模拟数据，不能证明真实 WPS / OpenCode / 远程模型提速。** 如果提供商将请求串行排队，并发 2 也可能没有收益。

实际验证请使用同一份未修改文档、相同选区、模型、深度增强和规则设置，分别选择并发 1 和 2，开启计时，每组运行前清空并复制记录。最好交替重复数次，比较 totalMs、各批 requestMs、审批轮询次数以及结果列表。真实 WPS 加载、复制兼容性、模型限流与耗时尚未在本次自动化测试中验证。
